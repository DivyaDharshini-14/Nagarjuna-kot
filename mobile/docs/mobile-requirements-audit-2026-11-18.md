# Nagarjuna Waiter and Kitchen mobile requirements audit

**18 November 2026 · Current working tree based on commit `f94495f` · Android emulator and local MySQL**

**Verdict: the two mobile apps implement the main service workflows, with confirmed gaps in kitchen routing, cancellation data consistency, stock-history presentation, history coverage and local notification delivery. Production acceptance is still open.**

The baseline is the supplied *Nagarjuna – Restaurant KOT Management System*, “Final Software Requirements & Development Scope,” sections 1–17. Sections 2 and 17 explicitly name an Android Waiter app and a browser-based Kitchen Display System (KDS). For the separately developed Kitchen Android app, this audit applies the kitchen operator, inventory, access and synchronization requirements. TV registration and TV-specific behavior are identified separately. Billing integration is excluded as requested in the project discussion.

**Evidence levels.** “Observed” means a screen or stored record was inspected. “Implemented” means a reachable mobile workflow and its relevant API path exist in the current source. “Partial” identifies a specific limitation. “Unverified” identifies an outcome that needs a controlled run. Historical records can demonstrate an outcome but cannot identify which app version or client originally produced it.

## What was verified

- Both Flutter apps passed fresh Dart analysis. On the emulator, the signed-in Waiter app showed the Indiranagar floor list and occupied orders. Opening an existing order and its add-items menu showed the expected table, dish prices, food types and tracked portions.
- **The same live record agreed across the apps.** The Waiter app showed ORD-0013, Table Three 3, one Chicken Biryani, Accepted, Biryani Kitchen, KOT-5. The Kitchen board showed the same identifiers, dish, quantity and state, plus receipt time and elapsed time. This verifies the read path. A newly generated state transition was not timed.
- The signed-in Kitchen app showed the assigned-station board, stage filters and prepared stock. Chicken Biryani showed four portions on both the Waiter menu and Kitchen stock screen. Untracked dishes on the Kitchen screen explained the tracking prerequisite.
- Read-only queries for Indiranagar found 7 tables, 6 kitchens, 26 orders, 46 KOTs, 31 cancellation records and 54 stock transactions. One order had tickets for at least three distinct kitchens. The branch had no dish currently mapped to multiple active kitchens, so the multi-kitchen-dish finding below is from source.
- Earlier emulator checks in this project session covered Kitchen network loss and recovery, automatic refresh, History navigation, search, filtering and local pagination using 22 sample tickets. The installed live build was subsequently reopened. These are separate from physical-device and production checks.
- This review used existing sessions and read-only business data. A new order, cancellation, stock adjustment, account transfer or production push was not submitted. Project guidance assigns automated testing to the owner. Existing test files were inspected as coverage evidence rather than counted as passing tests.

At inspection, 38 broadcast jobs and 60 KOT push jobs were queued. A connected socket or a current screen does not establish prompt event delivery. Foreground polling can still update the display. The history row displays “wastage · 0” and the unchanged balance, omitting the positive quantity wasted. | [History row](../../kitchen_mobile/lib/presentation/kitchen_stock_screen.dart#L563) · [Ledger write](../../app/Services/OrderService.php#L941) |

KOT numbers are chosen per branch/day under kitchen locks. Additions on different orders targeting different kitchens can choose the same displayed number. The migration removes the unique KOT-number constraint. Separately, the Kitchen API checks a ticket transition before the service writes it, leaving a race with another update or cancellation. ## Waiter requirements

| Specification | Assessment |
|---|---|
| §§1, 2B, 4, 5.1 — registered login, company, branch, role | **Implemented.** Email/password sign-in, secure token storage, restore, expiry handling and logout are present. The API checks active account and organization, roles and permissions; order and menu reads are tenant-scoped. An existing authenticated session was observed. Fresh login, revocation and cross-branch isolation still require acceptance checks. |
| §§3.4–3.5, 5.2 — floor or table list, status, select available table, open order | **Implemented.** Floors and tables show names, seats and current backend status. Available tables open the composer in one tap. Occupied tables open order progress or allow additions. The model recognizes available, occupied, reserved and cleaning; the server checks table capacity, locks the table and rejects conflicting open orders. |
| §§3.6–3.8, 5.3 — categories, search, category filtering | **Implemented.** The API scopes active menu data to the organization and branch, groups and sorts it, and the composer applies category and dish search. The emulator displayed eight menu items across the offered categories. |
| §5.3 — images, selling price, stock, sold-out state, Veg/Non-Veg | **Implemented.** Configured images load from the storage URL with a fallback for absent/failed images. Price and food type are visible. Tracked quantities, zero stock, unconfigured tracking and explicit availability govern adding a dish. Prices, Veg/Non-Veg labels and available quantities were observed; a live sold-out transition is pending. |
| §5.4 — select dishes and quantities, special instructions, item notes, review and submit | **Implemented.** Quantity controls, per-line notes, an order-level instruction field, cart review, guest count, totals and submit are connected to the order API. One cart entry is maintained per dish, so a note applies to all portions on that entry. The specification does not explicitly require different notes for individual portions of the same line. |
| §5.5 — save order and lines, unique number, KOT split, stock, push, confirmation | **Partial end to end.** A transaction saves the order and lines, consumes tracked stock, generates KOTs and queues change events. Confirmation lists the order number and kitchen tickets. Routing, concurrency and delivery limitations are detailed above. |
| §5.6 — additional dishes on the same order, new KOTs, no replacement or duplicate deduction | **Implemented for the standard path.** The add-items endpoint locks the existing order and table, adds lines, deducts new stock and passes only the newly created lines to KOT generation. The composer and quantity increase flow retain request keys for retry. Four local orders had more tickets than distinct kitchens; this is consistent with later tickets but is not proof of exactly-once replay. |
| §5.7 — New, Accepted, Preparing, Ready, Served, Cancelled for each item | **Implemented in the UI; partial in persistence.** Per-item states and authorized marking of ready items as served exist. The app accounts for fully cancelled quantities. The matching Accepted ticket was observed in both apps. See the stored-status finding above. |
| §§2B, 5.7 — waiter receives kitchen-ready notifications | **Partial in this environment.** Order progress subscribes to the private order channel and refreshes every 12 seconds. Newly ready items can trigger an in-app notice. The original waiter also has a Firebase notification path when away from that order. Local server push configuration is incomplete. |
| §8 — cancel a dish, selected quantities or a whole order; mandatory reason | **Implemented, with the retry limitation above.** Authorization, the reason, available quantities, cancellation decisions and kitchen events are handled. The current Indiranagar setting allows direct cancellation. A branch configured to require approval still returns a pending decision. |
| §§4, 8, 11 — approval permission and cancellation policy | **Implemented as a server policy.** Authorized approve/reject endpoints exist. Approval controls were deliberately removed from the Waiter app at the owner's request. The specification requires controlled permission; it does not assign an approval inbox specifically to the Waiter phone. |
| §8 — modify an existing order and retain history | **Implemented with limits.** Add dishes or portions; reduce portions through reasoned cancellation; edit item instructions while all relevant KOT lines are new or accepted and no cancellation is pending. The service updates existing KOT instructions and emits change events. History visibility is limited as described above. |

## Prepared stock across both apps

| Specification | Assessment |
|---|---|
| §7.1 — opening stock and stock in | **Implemented.** Authorized kitchen staff enter quantities and reasons. The first increasing movement on unconfigured tracked stock records opening stock; subsequent additions record stock in. The local ledger contained both types. |
| §7.2 — deduct ordered quantity only on successful submission | **Implemented in source, supported by ledger evidence.** Quantities aggregate per dish, tracked menu items are locked, and deductions and their ledger entries are inside the order transaction. Ten local order-deduction records existed. |
| §7.3 — latest stock, warning, block excess, edit order, prevent negative balances | **Implemented.** The composer limits quantities and reconciles the cart on refresh. The API rechecks aggregate quantities under lock, rejects excess with the available quantity and rolls back. The menu refreshes by branch event and 15-second polling. Actual simultaneous last-portion contention remains a UAT item. |
| §7.4 — increase/reduce, wastage, damaged or spoiled food, corrections, actor, timestamp, quantity, reason | **Implemented for recording.** Stock-in, wastage, damaged and directional correction controls exist. The API requires positive quantity and a reason, rejects negative balances, and records actor, timestamps, before/after and delta. Spoiled portions can be recorded with the applicable movement and reason. See the history-display and retry gaps. |
| §7.5 — complete transaction history | **Partial in the Kitchen UI.** The ledger supports opening stock, stock in, order deduction, cancellation reversal, wastage and manual adjustment. All six occurred locally. Stock and movement history support server-side pages of 50. The UI omits affected quantity for zero-delta wastage. |
| §7.6 — available, temporarily unavailable and sold out reach the waiter | **All states implemented; immediate delivery conditional.** Kitchen changes record a reason and emit a menu event. The Waiter composer subscribes to the branch menu and reconciles quantities; polling supplies fallback. A fresh two-device availability change was not made during this audit. |
| §7.7 and §8 — exactly-once order deductions, cancellation reversal and prepared-food wastage | **Implemented for keyed creates/additions and ordinary cancellation processing.** New or accepted portions are eligible for return to tracked stock. Preparing and later portions are recorded as wastage with no extra stock deduction. Across the 31 local cancellation records, 42 portions were approved, 17 classified for return and 25 classified as wastage. Actual reversal movements depend on stock tracking. Cross-device replay of the cancellation itself remains a separate gap. |

| §9 and §16 — billing and excluded functions | External billing integration was excluded by the owner. Invoice creation, payment collection, accounting/GST, raw material and recipe inventory, purchasing/vendors, online consumer ordering and delivery integration are phase-one exclusions. |

| §11 — settings | Staff consume branch scope, order/KOT numbers, stock and cancellation policies. The inspected number generators use fixed formats. | §13 — non-functional requirements | Phone layouts, secure token storage, scoped APIs, release HTTPS checks, reconnection, transactional stock handling and keyed order retries are implemented. Responsive web layout is a web deliverable. |
| §14 — development phases | Phases 1–2 supply the configuration consumed by the apps. Phases 3–6 map to the ordering, routing, kitchen and stock matrices above. Phase 7 is excluded here. Phase 8 is primarily management. Phase 9 requires release/UAT evidence beyond the available debug builds. |
| §17 — deliverables | Android apps and readmes, mobile implementation plans and a readiness checklist exist. The Kitchen README references API, operations and Kitchen UI acceptance documents absent at the named paths in this checkout. This limits documentation handoff. Database documentation completeness, browser/admin delivery, deployed production configuration and UAT sign-off were not certified here. |

**Owner-requested day boundary.** The Kitchen phone filters by the ticket's creation date in the restaurant time zone. An unfinished ticket from before midnight disappears from the phone after rollover, even though it still exists on the server. The Waiter table list reflects the real open order and table state. Its API gives the active order ID and number; order detail gives an update timestamp but omits order creation time. The app uses the earliest known activity, so an older order first seen after a same-day update can look current. These are service-policy implications of the requested today-only behavior. ## Section 15 acceptance record

The numbers follow the twenty scenarios in the specification, in order.

| Scenarios | Evidence and outstanding acceptance |
|---|---|
| 1–3. Create companies/branches, create kitchens, assign dishes | Master setup is management-owned. Existing branch, six kitchens and assigned dishes were observed. A fresh multi-company setup and changes to mappings were not performed. |
| 4–5. Place a three-kitchen order and verify each kitchen receives its own dishes | Existing data includes one order spanning at least three kitchens; one ticket was matched between both apps. A controlled three-station comparison remains open. A dish mapped to two stations fails by source inspection. |
| 6. Same KOT not duplicated | Server replay protection exists for the original keyed request. Concurrent numbering and a repeated request must be checked independently. Duplicate visible numbers and duplicate ticket records are different failures. |
| 7–8. Add to an existing order and receive new KOTs | The existing-order composer was observed. The server explicitly tickets only new order lines. A controlled before/after and retry with unchanged earlier tickets remains pending. |

| 11–12. Add prepared stock and verify order deduction | Stock controls and both movement types were observed. The two phones agreed on a current quantity. A fresh balance-to-order-to-ledger reconciliation is still pending. |
| 13. Reject insufficient stock | Client controls and locked server validation were inspected. A simultaneous last-portion order and a mixed cart that must roll back all lines still require controlled acceptance. |
| 14. Cancellation and stock reversal | Local data confirms return and wastage classifications. Full and partial cancellations across preparation states, uncertain responses and raw status consistency remain acceptance issues. |
| 15. Sold-out dish disabled | UI and server checks exist. A fresh Kitchen-to-Waiter availability switch, cart reconciliation and attempted checkout were not exercised in this audit. |
| 16. Branch-wise access restrictions | Normal scoped queries and permissions were inspected. Two independent branch accounts, role changes and reassignment still require controlled acceptance. |
| 17. Kitchen display reconnects | Earlier Android emulator checks covered loss and recovery. Browser TV reconnect and a newly issued KOT during an outage still require acceptance. |
| 18. Billing API authentication and synchronization | Excluded by the owner. |
| 19. Retry without another order or stock deduction | Mobile key persistence, server uniqueness and replay behavior were inspected. Controlled lost-response/restart and concurrent retries with ledger counts remain unverified. |

**Release assessment.** Routine ordering and kitchen processing are implemented and demonstrable. Multi-kitchen routing, stored cancellation consistency, wastage presentation and notification delivery are concrete reasons to withhold full mobile acceptance. Physical-device, concurrent-use and remaining §15 scenarios still need recorded results.
